# Deployment

This repository contains only the Frappe **app** source; it does not include any deployment manifests (no `Dockerfile`, `docker-compose.yml`, Kubernetes manifests, Nginx config, Supervisor config, or CI/CD pipeline definitions were found in the repository — confirmed by directory search). Deployment is entirely governed by the standard Frappe/`bench` deployment model described below; nothing here is app-specific beyond "install this app into the bench like any other."

## Development Deployment

Standard `bench` development workflow:

```bash
bench start
```

This runs Frappe's built-in development web server, Redis, the background worker(s), and the scheduler (if enabled) as foreground processes managed by `honcho`/`Procfile`, plus a `bench watch` process to rebuild frontend assets on change. This app requires no additional dev-mode process of its own — it has no separate service, worker, or long-running process defined in `hooks.py` (no `scheduler_events`, no custom workers).

Live-reload of this app's client scripts happens automatically because they're referenced via `doctype_js` and served through Frappe's standard asset pipeline.

## Production Deployment

Standard `bench` production setup (via `bench setup production <user>`) generates:
- **Nginx** — reverse proxy + static asset serving (config generated by `bench`, not present in this repo).
- **Supervisor** — process manager for Gunicorn workers, background workers, and the scheduler (config generated by `bench`, not present in this repo).
- **Gunicorn** — WSGI server running `frappe.app`.

None of these are defined inside this repository; they are bench-managed and environment-specific. If this app is deployed to a managed/hosted Frappe environment (e.g., Frappe Cloud), those platforms provide their own equivalents.

```bash
sudo bench setup production <frappe-user>
sudo supervisorctl restart all
```

## Workers

Frappe's default worker queues (`short`, `default`, `long`) are started via `bench worker` / Supervisor. **This app enqueues no background jobs** — no `frappe.enqueue(...)` calls were found anywhere in the app's Python source (confirmed by repository-wide search). All logic executes synchronously within the request/response cycle (form save, submit, or whitelisted RPC call). This has performance implications for large operations — see `docs/known-limitations.md` (e.g., `bulk_ra_billing.py`'s bulk-generation logic and `bill_of_quantities.py`'s import/costing-sync methods run inline rather than as background jobs).

## Scheduler

`hooks.py` defines the `scheduler_events` block only as a **commented-out template** (`hooks.py:304-323`); no scheduled/cron-style jobs are registered by this app. The site-wide Frappe scheduler (used by ERPNext and Frappe core for other periodic jobs) still needs to be enabled (`bench --site <site> scheduler enable` / `resume`), but nothing in this app depends on it. See `docs/scheduler-and-background-jobs.md`.

## Nginx

Not found in repository. Standard `bench setup nginx` output applies; no app-specific rewrite rules, custom routes, or static-asset overrides are defined here.

## Supervisor

Not found in repository. Standard `bench setup supervisor` output applies; no custom process definitions (e.g., dedicated worker queues for this app) are defined here.

## Migrations During Deployment

Every deployment/update should run:

```bash
bench --site <site-name> migrate
```

This applies any new DocType schema (JSON) changes and re-syncs fixtures. As noted in `docs/installation.md`, `patches.txt` currently defines no data-migration patches, so `migrate` for this app reduces to schema sync + fixture sync.

## Asset Build on Deploy

```bash
bench build
```

Rebuilds/bundles static assets for all installed apps, including this app's `public/js/*.js`. There is no app-specific build step beyond what Frappe's asset pipeline does automatically.

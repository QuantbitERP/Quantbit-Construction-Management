# Known Limitations

All items below are concrete findings from reading the source code (via 7 parallel deep-research passes covering all 131 DocTypes plus the app-root modules), not speculation. Cross-references point to where each is discussed in more depth.

## Technical Debt

- **No automated test suite.** No `test_*.py` files, no `tests/` directory. The only test-shaped artifacts, `public/pythonn/check_stages.py` and `public/pythonn/test_clone.py`, are standalone scripts using `frappe.init()`/`frappe.connect()` directly rather than `FrappeTestCase` — they are not discovered by `bench run-tests`. `test_clone.py` additionally imports a function, `create_stage_from_template`, that **does not exist** in `api.py` — this script is provably stale/broken. See `docs/developer-guide.md#how-to-write-tests`, `docs/troubleshooting.md`.
- **Live whitelisted Python endpoints under `public/`.** `public/pythonn/stock_entry.py` contains two `@frappe.whitelist()` functions (`has_dependencies`, `get_depends_on_tasks`) that are actively called from `Stock_Entry.js`. `public/` is conventionally reserved for static assets served by the Frappe asset pipeline; placing live business-logic endpoints there is a structural inconsistency with the rest of the app (every other whitelisted method lives in a DocType controller or an app-root utility module). See `docs/api-reference.md`.
- **Two "RA Billing" concepts with the same name in different modules.** `subcontractor_management.doctype.ra_billing` (a submittable running-account bill, ~2710-line controller) is a distinct DocType from the `ra_billing` **module**'s doctypes (`Bulk RA Billing`, `Task Level Sheet`, etc.), which *consume* the former via a Link field (`Bulk RA Billing Projects Details.ra_bill` → options "RA Billing"). The shared name across module and DocType boundaries is a significant source of confusion for new contributors and for search/documentation tooling. See `docs/modules.md#ra-billing`.
- **`task_bom_details` (Tendering module) has a `.py` controller but no `.json` definition** — an incomplete/orphaned DocType folder that cannot actually register as a valid DocType without its JSON.
- **`MS Activity` (Quality and Safety Management) is an orphaned child table** — no parent DocType's JSON in this module references it as a Table field.
- **Duplicate `delete_task_with_dependencies` implementations** exist in both `api.py` and `bill_of_quantities.py`, with the same name and near-identical logic, invoked from different UI surfaces (Project hierarchy widget vs. BOQ form) — a candidate for consolidation into a single shared helper.
- **Dead, commented-out duplicate function**: `site_diary.py` has a fully commented-out `update_daily_activity_progress_table` (lines ~382-383) sitting immediately before the live, whitelisted version of the same function (line 451) — should be deleted rather than left as a comment.
- **Malformed Select field `options` strings** in Quality and Safety Management: `NCR.ncr_type` lists "Non-Conformance" twice; `Incident Report.incident_type` and `Safety Observation.observation_type` have options that read as run-together phrases (likely a missing newline separator when the option list was authored) — worth a data-quality pass on those Select fields.
- **Frappe version not pinned**, and the **ERPNext dependency is not declared** in `hooks.py`'s `required_apps` despite being a hard runtime requirement (`overrides/task.py` imports directly from `erpnext.projects.doctype.task.task`, and five `doc_events` target ERPNext DocTypes). `bench install-app` will not stop someone from installing this app without ERPNext already present, only to fail at runtime. See `docs/installation.md`, `docs/project-overview.md`.
- **Excel handling (`openpyxl`-shaped usage) is not declared as a dependency** in `pyproject.toml`, despite multiple whitelisted methods reading/writing `.xlsx` files (`docs/integrations.md`).

## Performance Concerns

- **No background job usage anywhere.** Every whitelisted method, including the heaviest ones (`bulk_ra_billing.export_bulk_ra_excel` at ~950 lines, `bill_of_quantities`'s 14 methods, `ra_billing.py`'s Excel/level-matrix methods), runs synchronously in the request/response cycle. As project/task counts grow, these are likely to approach or exceed default web-worker timeouts. See `docs/scheduler-and-background-jobs.md`, `docs/troubleshooting.md`.
- **Client-side recursive cost/progress roll-ups over `frappe.client.get_list`.** `Project.js`'s hierarchy widget fetches up to 1000 Tasks per Project (`limit_page_length: 1000`) and recomputes the entire cost/progress tree client-side on every expand/collapse interaction, with additional round-trips (`frappe.call({method: "frappe.client.set_value", ...})`) fired per-node when progress changes — this does not scale gracefully to very large/deep Task trees and generates significant chatty traffic.
- **No dedicated indexes beyond JSON-declared `unique`/`search_index` flags** (42 and 27 fields respectively) — the app's heavier aggregate queries (child-table joins in `docs/reports.md`, the RA Billing engine's task/date-range lookups) rely entirely on Frappe's default indexing (primary key + `parent`/`parenttype`/`parentfield` on child tables). See `docs/database.md#indexes`.
- **`update_task_material_cost` (Stock Entry hook) reads-modifies-writes via `frappe.db.get_value`/`frappe.db.set_value` in a loop** rather than a single aggregate `UPDATE`, and lacks any locking — concurrent Stock Entry submissions touching the same Task could race (last-write-wins on the "add to existing total" logic, since the read and write are not atomic).

## Duplicate Code

- See "Duplicate `delete_task_with_dependencies` implementations" above.
- **Two independent progress-rollup implementations** for the Task hierarchy: `Project.js`'s client-side `calculate_progress()`/`compute_costs()` and `Daily Progress Tracking`'s server-side `update_parent_progress` (core module) compute conceptually the same weighted roll-up via different code paths, with no shared source of truth — they can diverge if one is updated without the other. See `docs/database.md#the-task-hierarchy-central-data-model`.
- **Multiple near-identical `has_dependencies`/`get_depends_on_tasks` Link-query pairs** are copy-pasted (not shared via a common utility) across `site_diary/doctype/task_progress/task_progress.py`, `site_diary/doctype/equipment_usage/equipment_usage.py`, `site_diary/doctype/manpower_usage/manpower_usage.py`, `public/pythonn/stock_entry.py`, and `ra_billing/doctype/task_level_sheet/task_level_sheet.py` — a strong candidate for consolidation into a single shared helper (e.g., in `api.py`).

## Missing Validations

- **The 100%-sibling-weight cap on Task hierarchy nodes is enforced only in `Project.js`**, not in any Python controller (`overrides/task.py`'s `CustomTask` only validates the `status`/`depends_on` transition, nothing about `task_weight`). Any creation path that bypasses the Project form's dialogs (bulk import, direct API/Data Import, `bill_of_quantities.py`'s clone/duplicate methods) can produce sibling weights summing to more than 100% with no server-side rejection. See `docs/troubleshooting.md`.
- **`Tender.confidential_documents_details` is set to `permlevel: 4`, but no role in `Tender`'s permissions array is granted `permlevel: 4` access** (all seven roles listed are `permlevel: 0`) — this field is effectively inaccessible to every business role, including `Top Management`/`Business Head`, who plausibly should see confidential tender documents. Likely an incomplete permission configuration rather than an intentional lockout. See `docs/permissions.md`.
- **No row-level/tenancy permission logic** (`permission_query_conditions`/`has_permission` are template-only, never activated — `docs/permissions.md`) despite this being a multi-project (and, via the `Site` Accounting Dimension, multi-site) system where restricting a user's visible records by Project or Site would be a common real-world requirement.
- **Most Quality and Safety Management, Progress Measurement & Billing, and several other modules' controllers are entirely `pass`-only** (confirmed across all 15 QSM doctypes and all 7 Progress Measurement & Billing doctypes) — meaning status transitions, corrective-action workflows, earned-value formulas (SPI/CPI/EAC), certificate net-certified amounts, and claim financial roll-ups are **stored fields with no code that computes or validates them**. Anything currently populating those fields is doing so manually via the UI, with no guarantee of internal consistency. See `docs/modules.md`.
- **`Stock Entry.on_cancel` is not hooked**, so `custom_total_material_cost` is never decremented when a Material Issue Stock Entry is cancelled (see `docs/troubleshooting.md`) — a missing validation/reversal, not just a missing feature.

## Refactoring Opportunities

- Extract the repeated `has_dependencies`/`get_depends_on_tasks` Link-query pair (see "Duplicate Code" above) into a single shared, parameterized utility.
- Move `public/pythonn/stock_entry.py`'s whitelisted functions into a proper controller/utility module location.
- Consolidate the two progress-rollup implementations (client `Project.js` vs. server `Daily Progress Tracking`) behind one server-side source of truth, with the client calling it rather than reimplementing the math.
- Introduce `frappe.enqueue(...)` for the heaviest whitelisted methods (bulk Excel export/import, BOQ duplication) rather than running them synchronously.
- Add a server-side `validate()` (or a `before_insert`/`before_save` hook on `Task`) enforcing the sibling weight-cap rule that today lives only in `Project.js`.
- Resolve the `"Tender created"` vs. `"Tender Created"` casing mismatch (`docs/workflows.md`) by introducing a shared constant instead of repeated string literals.
- Delete stale artifacts: `public/pythonn/test_clone.py`'s dead import, the commented-out duplicate `update_daily_activity_progress_table` in `site_diary.py`, and the orphaned `task_bom_details`/`MS Activity` doctype folders (or complete them properly if they're intended to be used).
